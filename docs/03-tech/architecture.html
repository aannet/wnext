Architecture WNEXT : front, back, base

Comment l'écran, l'API et PostgreSQL se parlent aujourd'hui, ce qui tourne en local, et ce que la production exige déjà du code. Relevé sur le code le 2026-10-24. Le détail des routes est dans la doc API.

Front : React + ViteBack : Node.js node:http + pgBase : PostgreSQL ≥ 15Contrat : Zod → OpenAPI (ADR-003)

Vue d'ensemble

Trois processus, plus le fournisseur d'identité. L'API est un seul processus sur un seul port : REST et WebSocket ensemble. Elle ne garde aucun état métier : tout est en base. Le temps réel ne fait que diffuser des références ; les écritures passent toujours par REST.

Écriture et propagation en temps réel

Exemple : A déplace une allocation, B voit le bloc bouger sans recharger la page. Objectif : moins d'une seconde. La notification n'arrive qu'au COMMIT, donc jamais pour une écriture annulée. Si une notification se perd, le sondage d'une seconde rattrape le changement.

Code et contrat

Monorepo TypeScript. Le contrat est la seule source de vérité partagée (ADR-003) : le front et le back ne s'importent jamais, ils ne connaissent que contracts et engine. Le lint de frontières (boundaries.config.mjs) le vérifie dans make check.

Sécurité et isolation

Isolation des comptes

  • Chaque transaction pose SET LOCAL ROLE app_user et app.account_id, app.user_id, app.role : la RLS de PostgreSQL filtre toutes les tables.
  • Le compte vient de la session, jamais d'un paramètre de requête ni d'un message temps réel.

Droits dans le compte

  • Rôles owner, admin, pm, member (account_members), distincts des personnes planifiables (ADR-002).
  • Le PM écrit seulement sur ses projets (BR-33). Le member ne lit que sa personne liée, en REST comme en temps réel (scope.ts, RT-048).

Authentification

  • L'API ne voit qu'un jeton d'accès JWT : elle vérifie signature, émetteur, audience et expiration. Elle ne gère ni mot de passe ni session.
  • WebSocket : ticket signé, valable 30 s, demandé par POST authentifié (un navigateur ne peut pas poser d'en-tête sur un WebSocket).

Pile locale

Aucun Docker : Postgres est embarqué (embedded-postgres). Commandes et pièges : runbook de démarrage local.

Production : à décider

Aucune infrastructure de production n'existe ni n'a été décidée par ADR. L'intention date de la revue d'architecture v1.1 (archi-solution §1.10) : conteneurs, au moins 2 instances sans état derrière un répartiteur, PostgreSQL managé avec PITR en région UE, SPA sur CDN, infrastructure en code (OpenTofu/Terraform), environnements preview → staging → prod.

Déjà exigé par le code en place

  • NODE_ENV=production refuse AUTH_MODE=dev, une URL JWKS sans https et l'absence de WS_TICKET_SECRET, qui doit être partagé par les instances.
  • Arrêt propre sur SIGTERM : plus de nouvelles connexions, WebSocket fermés, requêtes en cours terminées, arrêt forcé au bout de 10 s.
  • Journaux JSON sur la sortie standard, avec l'identifiant de requête, jamais le corps ni les en-têtes.
  • RLS active seulement sous un rôle non propriétaire : DB_ROLE=app_user, ou une connexion directe en app_user.

Limites connues avec N instances à traiter

  • Les limites de débit et le plafond de connexions WebSocket sont comptés par processus : avec N instances, la limite effective est jusqu'à N fois la valeur configurée.
  • L'usage unique d'un ticket n'est garanti que dans un processus (tickets.ts) ; le garantir partout demanderait un stockage partagé.
  • Migrations : scripts/migrate.mjs contrôle les sommes SHA-256 ; la stratégie expand/contract sans interruption n'est pas outillée.
  • Pas encore : sauvegardes managées, supervision, tests de fumée après déploiement (P5).
