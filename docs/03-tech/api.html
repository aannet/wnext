WNEXT API interne v1.0.0

104 opérations REST JSON sous /api/v1, plus un canal temps réel en WebSocket. Page générée par npm run generate:contract depuis packages/contracts (Zod, ADR-003) : ne pas l'éditer. La spec brute est packages/contracts/openapi.json ; le client TypeScript généré est apps/web/src/api/client.gen.ts.

  • Écritures avec verrou optimiste : l'en-tête If-Match porte la version lue ; une version périmée répond 409 VERSION_CONFLICT, son absence 428 PRECONDITION_REQUIRED.
  • Le compte vient toujours de la session (RLS PostgreSQL), jamais d'un paramètre.
  • Les réponses ne portent jamais de texte d'interface : l'écran traduit les codes.

Authentification

  • Production (AUTH_MODE=oidc) : Authorization: Bearer <JWT> émis par le fournisseur d'identité OIDC. L'API vérifie la signature (JWKS), l'émetteur, l'audience et l'expiration, puis relie sub à users.idp_subject. Ni mot de passe ni session côté API.
  • Développement (AUTH_MODE=dev, refusé en production) : en-têtes x-dev-*, sans preuve.
  • Temps réel : un navigateur ne peut pas poser d'en-tête sur un WebSocket ; il demande un ticket à usage unique (voir Temps réel).

Erreurs

Toute erreur répond un ApiError : code stable, params (valeurs utiles à l'écran) et requestId (à citer dans un signalement). Codes :

  • VALIDATION_FAILED
  • UNAUTHENTICATED
  • SCHEDULE_RANGE_INVALID
  • SCHEDULE_CURSOR_INVALID

Temps réel

Le canal ne fait que diffuser : aucune écriture par WebSocket. Un message ne porte que des références (entité, id, version) ; le client recharge l'entité, ou ignore le message si sa copie est déjà à cette version. Source : l'outbox change_log. Contrat complet : packages/contracts/src/realtime.ts (hors spec OpenAPI).

Chemin WebSocket/api/v1/realtime
Ticket d'upgradePOST /api/v1/realtime/ticket, puis ?ticket=… ; valable 30 s, une seule connexion
Version du protocolev = 1
Refus à l'upgrade401 non authentifié · 404 mauvais chemin · 429 plafond ou débit (Retry-After ≥ 5 s) · 500

Déroulé : le client envoie subscribe avec son curseur (le changeCursor de GET /api/v1/schedule, puis le dernier reçu) ; le serveur rattrape par lots changes, envoie ready, puis diffuse en direct. Un curseur trop ancien reçoit resync : recharger le planning et se réabonner.
